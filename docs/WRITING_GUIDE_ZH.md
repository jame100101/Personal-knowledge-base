# 中文教学写作约定

知识库面向正在学习开发的人。用词可以专业，但读者应先知道正在解决什么问题，再接触解决它的术语。写作时想象自己正在向同事解释一段代码：说清楚发生了什么、该看哪里、为什么这样做，就足够了。

## 从已有材料改起

先读完整小节，列出它必须保留的事实、条件和动作。修改的是表达，不是知识结论。没有出处的新案例、版本、性能数据和作者经历，不为“写得生动”而添加。原文说“可能”“通常”“仅在……时”，改写后仍要保留这个范围。

代码、命令、路径、行内代码、链接、版本记录、表格、引用、标题和锚点按原样保留。如果确实发现技术错误，另行查证并记录依据，不混在文风润色里偷偷修正。例子中的失败也要保留，不能为了让过程流畅就删掉失败条件。

## 让读者跟得上

遇到术语堆叠，先把动作讲清楚，再给术语。英文 API、框架名和协议名保留，方便读者查文档；不要把技术含义不同的词换成一个听起来轻松的比喻。

本轮的一个实际改写：

> 原文：关键不变量是每个调用 ID 与结果对应。并行调用时，也要保持协议要求的结果集合和顺序。
>
> 改后：每份工具结果都要对应原来的调用 ID，这个关系不能丢。即使多个工具并行执行，回传时也要满足协议对结果集合和顺序的要求。

这里把“不变量”说成了要一直保持的对应关系，协议要求没有被省略。原本顺畅的场景开头可以保留，不必把所有文章都改成问句，也不必每段都安排一个故事。

另一个例子：

> 原文：自动化测试需要稳定定位、独立数据、并行能力、失败证据和责任闭环，脚本数量本身不代表质量。
>
> 改后：自动化测试要能稳定找到目标，使用互不干扰的数据，并支持并行运行。失败后要留下可查的记录，也要明确由谁处理。脚本写得多，并不代表这些问题已经解决。

## 少一点固定腔调

连续小节不必都以“这里容易混淆的是”开头。后面的限制本来就讲得清楚时，直接说限制。不要再换成另一套统一的“注意一下”“说白了”“记住一句话”。

连接词、列表、粗体、破折号和“不是……而是……”都有用途。能帮助说明步骤或纠正误解，就保留。不要为了降低某个词的出现次数，把完整的教程改成零碎短句，也不要把所有专业词换成口语。

标题和列表负责帮助查找，正文负责解释。一个小节如果只有名词清单，优先解释其中的关系和作用；需要新增知识才能解释时，先补来源。结尾可以停在操作、检查结果或适用限制上，不必再升华一次。

## 项目采用哪些上游规则

本项目以 [op7418/Humanizer-zh 的 2026-09-23 修订](https://github.com/op7418/Humanizer-zh/blob/f4518a8eab97b8bfebc66a89d34320a89bef6930/SKILL.md) 为主要编辑依据，采用其保留信息、确定程度和文件结构的约束。

另参考 [ai-zixun/humanizer-zh](https://github.com/ai-zixun/humanizer-zh/tree/f75f1ac9735c4f10da1bba0148e0ea7228c5c3b3) 的句子和文章组织检查，以及 [syw2039/humanizer-zh](https://github.com/syw2039/humanizer-zh/tree/72d73f9c8132817e21f66369de6925a659f9a6a6) 的事实核对清单。上游部分示例会补入原句没有的细节，或把不确定的判断改得更肯定；这些示例不作为本项目的改写范本。有关作者口吻模仿、统一日期写法、禁用标点的建议也不启用。技术准确性和已有来源优先。

三个项目的选定文件及许可证保存在 [tools/humanizer](../tools/humanizer/README.md)。它们是编辑参考，不能用来证明作者身份，也不能替代技术审查。

## 编辑和发布

1. 编辑前记录 Git 基线，运行 `npm run content:style` 找到值得阅读的段落。
2. 通读上下文后改写，逐段比较原意。不要按检查结果批量替换术语。
3. 运行 `npm run content:style:verify -- --base <基线提交>`，核对代码、来源、数字和文章结构。再人工检查工具无法判断的否定、条件与因果关系。
4. 提交前列出实际改动的文章、代表性前后对照和检查结果，保留没有必要修改的文章。
5. 发布时以固定文档 ID 和内容哈希生成清单，先检查远端冲突、备份，再同步正文。Vercel 部署不会自动把 Git 中的正文写进 Supabase；必须分别验证代码部署和线上文章。

工具的行号提示是编辑入口，不是必须消除的错误。完成标准是读者更容易理解，同时原本的知识仍然成立。
